# 总体技术规划书 V1.0 设计评审

评审日期：2026-09-29。评审对象：`Windows游戏侧边栏视觉辅助软件-总体技术规划书-v1.0.md` 的原 V1.0 内容。

**归档说明（2026-09-29）：** R01–R12 已合并到同文件的 V1.1 修订正文，下文保留原始评审判断作为历史依据。后续开发以计划书 V1.1 和更新后的 Phase 0–1 清单为准；“规范已修订”不代表实现或真机验证已完成。

本次为设计与官方接口资料审查，未执行 Windows 真机、Maa 或目标游戏实验。当前工作目录只有规划文档，尚无代码工程，也未初始化 Git。目标游戏名称、进程名和窗口匹配规则按用户要求暂时留空；Windows 验收设备尚未确认。

## 1. 评审结论

**总体架构可行，可以保留技术路线并开始 Phase 0–1；但当前文档还不足以直接作为实现规格。** 主要问题是窗口身份、坐标语义、状态恢复和 Native 操作生命周期没有定义完整，直接实施会在 Phase 2–4 产生返工。

值得保留的设计：

- UI / Application / Core / 平台适配器分层。
- 窗口绑定与具体视觉业务分离，使用 Profile 管理布局。
- 外部截图和用户触发的前台自动化边界。
- Capture / Vision 分离，以及滚动采集 / 拼接分离。
- Mac 使用替身和 Fixture，Windows 真机负责最终兼容性验证。
- 有界实时分析、单任务自动化、本地数据、非 Single File 发布。

优先级说明：**高**表示会导致误绑定、错误坐标、无法停止或核心功能不可用；**中**表示应补规格以降低返工。以下建议不代表已经完成验证。

## 2. Phase 1 开工前应确定的问题

### R01｜高｜“第一阶段”与 Phase 1 的范围不一致

**位置：原文 §2、§38、§39、结论。**

§2 的“第一阶段”覆盖截图、自动化、滚动采集；§38 的 Phase 1 仅是窗口绑定。若不区分，Phase 1 的任务范围与验收范围会不断扩大。

建议将术语统一为：

- **V1 Framework：** Phase 0–10 的完整目标。
- **Phase 1：** 可诊断的窗口发现、手动选择、绑定、几何读取、Profile 校验、持续跟踪和失效恢复。
- 诊断主窗口和基础日志提前到 Phase 1；右侧跟随窗口仍属于 Phase 2。
- 游戏信息可空。先完成通用窗口绑定工程验收，再补目标游戏验收；二者不能混为一个已完成状态。

### R02｜高｜GameSession 缺少身份代次、状态恢复及异步过期保护

**位置：原文 §6、§7、§11。**

仅保存 PID / HWND / IsAlive 不足以保证当前窗口仍是原对象。微软明确指出 HWND 可以被回收复用，`IsWindow` 也不能消除检查后窗口销毁的竞态。[IsWindow 官方说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-iswindow)

建议：

1. `GameSessionManager` 是唯一写入者，UI 和后续 Feature 读取不可变快照。
2. 增加 `SessionId`、`BindingGeneration`、`GeometryVersion`、`ObservedAt`。每次换绑/解绑先使旧代次失效，迟到的查询结果不得写回当前会话。
3. 每轮跟踪及正式操作前核对窗口所属 PID、可获取的进程创建时间及匹配信息。访问失败要返回原因，不能用缓存证明窗口有效；这些检查降低风险，但不能把外部窗口变成原子可锁定对象。
4. 补上 `NotConfigured`、`Unbound`、`NeedsSelection`、`Faulted`，明确解绑与停止搜索。窗口消失后进入 `GameLost`，仅在自动绑定模式且匹配规则有效时重新搜索。
5. `Ready` 只表示绑定有效、几何有效且尺寸匹配，不能代表截图、输入或游戏布局已经兼容。最小化、前台状态作为独立运行状态；恢复后必须重新校验。
6. 尺寸不支持时保持绑定和诊断；尺寸恢复后允许重新进入 Ready，不能一直卡在 `UnsupportedResolution`。

### R03｜高｜Geometry / DPI 的定义仍有歧义

**位置：原文 §6、§8–11。**

`ClientRect` 没说明是 Client 局部坐标还是 Screen 坐标；`WindowRect` 可能包含不可见边框，并受调用方 DPI 上下文影响。微软推荐用 DWM Extended Frame Bounds 获取可见外框。[GetWindowRect](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowrect)

此外，`GetDpiForWindow(gameHwnd)` 受游戏窗口的 DPI awareness 影响，可能返回 96 或系统 DPI，不能直接作为侧边栏缩放值。[GetDpiForWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getdpiforwindow)

建议在 Phase 1 确定以下字段：

| 字段 | 约定 |
| --- | --- |
| WindowBoundsPx | 操作系统窗口外框，Screen physical pixels |
| VisibleFrameBoundsPx | DWM 可见外框；读取失败时显式标注回退 |
| ClientSizePx | Client 宽高，physical pixels，Profile 校验依据 |
| ClientOriginScreenPx | Client 原点在虚拟桌面的物理坐标 |
| ClientBoundsScreenPx | Client 在 Screen 坐标下的完整矩形 |
| MonitorBoundsPx / WorkAreaPx | 所属显示器与工作区，允许负坐标 |
| TargetWindowDpi / Awareness | 目标窗口报告的 DPI 和 awareness，仅作为独立信息 |
| GeometryValidity | 有效、最小化暂不可用、读取失败等状态 |

Windows 几何读取必须在已验证的 DPI awareness 上下文中执行；不能将所有 Win32 返回值无条件命名为物理像素。Client 原点应通过 API 转换，禁止用标题栏高度猜测。[GetClientRect](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getclientrect)、[ClientToScreen](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-clienttoscreen)

Phase 2 的侧边栏推荐贴可见外框右侧；如果仍选择原始外框，也应明确间隙是设计结果。侧边栏宽高布局使用其自身 `RenderScaling`，不能套用游戏的 `DpiScale`。Avalonia 默认支持每显示器 DPI，但这不替代外部 Win32 坐标转换。[Avalonia Windows 文档](https://docs.avaloniaui.net/docs/platform-specific-guides/windows)

### R04｜高｜发现窗口、多候选和手动选择规则不完整

**位置：原文 §7、§8。**

“找到进程”不等于找到游戏渲染窗口。同一进程可能有启动器、弹窗、隐藏窗和多个主窗口；两个游戏进程也可能使用相同标题。

建议以顶层窗口枚举为入口，再核对进程和规则。exe 为主要筛选条件，标题/类名为可选约束；多个候选不得按枚举顺序静默选择。过滤本程序、不可见窗口、工具窗口及 DWM cloaked 窗口；有 owner 的窗口默认降低优先级或排除，但保留诊断原因和显式选择方式。最小化候选可显示，不用其暂不可用的几何误判成“不支持分辨率”。

手动选择后仍需校验窗口有效性、尺寸和 Profile。相同分辨率不能证明某个窗口属于受支持游戏。没有目标游戏配置时，允许标为“手动诊断目标”，不得由此获得正式自动化能力。

空规则意味着“未配置、自动发现停用”，不能等价于匹配所有进程。匹配规则与布局 Profile 分开存储，Profile ID 应包含游戏/布局身份，不能长期只用 `1920x1080`。

### R05｜中｜Mac 可开发的设计缺少窗口服务替身及项目构建约定

**位置：原文 §5、§26、§32、§36。**

原文只替换截图与输入，Phase 1 的 UI 仍依赖发现和跟踪。需要 `FakeWindowCatalog` / `FakeWindowGeometryProvider` 提供“出现、消失、移动、尺寸变化、重绑竞态”脚本场景。它们验证应用状态，不模拟 Win32 API。

首期建议只建 App、Core、Application、Platform.Windows 四个生产项目；Fake 放 App 的开发专用目录。先不建 Maa、Vision 或空 Feature 项目。采用统一 `net10.0`、平台 API 标注和运行时保护是一种可行方案，Mac 启动不执行 Windows 初始化。若改用 `net10.0-windows`，必须同步设计独立启动入口/条件引用，不能让跨平台 App 直接依赖更窄的 TFM。

## 3. 后续阶段必须修正的设计

### R06｜高｜截图与输入之间缺少完整坐标契约

**位置：原文 §9、§12、§14、§15。**

原文少了 `CapturePixel` 坐标。Maa 提供截图缩放及 `ScreenshotUseRawSize` 配置，因此不能默认图像大小等于 ClientSize。[Maa 官方头文件](https://github.com/MaaXYZ/MaaFramework/blob/main/include/MaaFramework/MaaDef.h)

建议 Phase 3 优先显式使用原始尺寸，并验证返回图像是否确实对应完整 Client Area；仍需记录截图裁剪原点、尺寸和 `FrameToClientTransform`。不能仅设置 raw size 就宣称映射成立。缩放、黑边、裁剪和 DPI 均由适配器负责。

帧和识别结果携带 `SessionId + BindingGeneration + GeometryVersion`。每次输入前检查它们是否仍有效；窗口变更后丢弃旧识别坐标。Profile 后续补游戏 UI 缩放、布局版本、语言等条件，不能仅凭分辨率判断布局一致。

### R07｜高｜CancellationToken 与 finally 不能证明 Native 输入能及时停止

**位置：原文 §15–18、§41。**

取消托管等待不等于取消已经提交给 Maa 的操作。启动时检查前台也不能防止运行中用户切走、弹窗抢焦点或窗口移动。Windows 对获取前台有明确限制，即使符合条件也可能拒绝。[SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)

建议 Phase 4 落实：

- 每个输入步骤前重新检查前台、会话、几何和 Profile；失焦即停止，不能持续抢回前台。
- 记录当前任务实际按下的键/按钮，仅释放自身持有的输入。长拖动分段或使用已验证的 Native 中止机制。
- 以锁定版本核对 Native stop 的作用范围、是否等待在途操作、资源销毁的线程安全性。超时后不得一边释放 Controller，一边让后台任务继续使用它。
- 清理使用独立的短超时，不能沿用已取消的任务 Token；清理失败进入 Faulted，禁止立即开始下一任务。
- 调用线程不阻塞 UI/热键消息循环，先测量正常与故障情况下的停止延迟，再给出“随时停止”的承诺；若 Native 卡死无法满足目标，再评估进程隔离。
- 普通权限作为产品约束保留；目标以更高权限运行时明确拒绝不受支持的输入。正常 Win32 输入也有权限边界。[SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

### R08｜高｜默认紧急停止热键不应包含 F12

**位置：原文 §18。**

如果使用 `RegisterHotKey`，`Ctrl + Shift + F12` 应修改。微软明确将 F12 保留给调试器，不建议注册为热键。[RegisterHotKey](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerhotkey)

可选默认值为 `Ctrl + Shift + F10`，但仍必须检查注册返回值并允许修改。注册失败时禁用自动化入口，不能只记日志；截图和窗口绑定继续可用。该功能随 Phase 4 首次输入能力交付，Phase 1 无需提前实现全局热键。

### R09｜高｜图像资源、丢帧和 Capture 调度缺少所有权规则

**位置：原文 §12、§13、§17、§20。**

`GameFrame.Image` 的具体类型、复制/借用语义和释放者尚未定义。若直接放 `Mat` 会让 Core 依赖 OpenCvSharp；若使用 Native 指针或池化内存，则必须规定其生命周期。

建议 Core 使用带格式、stride、尺寸和释放契约的中立帧数据；适配器负责 Native buffer 到帧的转换，Vision 内部转换为 Mat。每帧有唯一明确所有者，扇出必须复制或使用受控共享租约。

实时 Channel 需要显式 `Capacity=1 + DropOldest`；只有 Capacity=1 默认会等待，不等于 latest-frame-wins。丢弃、分析完成、停止及异常路径均释放资源，可利用 `itemDropped` 回调处理丢弃帧。[.NET Channels](https://learn.microsoft.com/en-us/dotnet/core/extensions/channels)

同一 Controller 的单次截图、持续截图、自动化截图统一调度。暂停需要等待在途操作退出，清空旧帧；恢复前校验绑定。实时预览可以丢帧，滚动拼接序列不能复用这套丢帧队列。长图再增加字节数/输出像素上限，不能只限制帧数。

### R10｜中｜最小化截图的 best-effort 可能改变目标窗口

**位置：原文 §14、§29。**

当前 Maa 文档说明部分最小化截图通过伪最小化方式实现，会修改透明/点击穿透状态并恢复窗口，不能将其理解为纯被动读取。[Maa 控制方式](https://github.com/MaaXYZ/MaaFramework/blob/main/docs/en_us/2.4-ControlMethods.md)

建议 V1 最小化时暂停 Capture 和自动化，恢复后重新校验；把最小化截图留为后续显式能力。后台但未最小化的截图继续按原计划验证。该策略也减少 GameSession 与 Maa 各自改变窗口状态造成的冲突。

### R11｜中｜侧边栏不可达与激活策略尚未定义

**位置：原文 §10、§11、§29。**

保留“只在右侧、不换边、不 Clamp”的产品决定，但在单屏无边框窗口占满屏幕时，侧边栏可能完全不可见。应保留独立主窗口/任务栏入口，用于展开、解绑和设置；不能让唯一操作入口随着侧边栏离屏。

跟随定位默认不抢焦点；明确 Z-order、是否置顶、切到其他应用后的显示行为，避免全局 Topmost 挡住其他应用。侧边栏可与游戏位于不同 DPI 显示器，需分别取缩放。

### R12｜中｜开发顺序应先验证可行性，再扩大框架

**位置：原文 §24、§32、§38。**

Phase 5 才提供截图诊断、Phase 9 才用实际功能验证抽象，风险发现偏晚。建议窗口诊断随 Phase 1、截图预览随 Phase 3、输入诊断随 Phase 4；Phase 3–4 用一个最小“用户触发截图→简单分析→显示”切片验证接口，不必提前做完整 Feature 注册系统。

目标游戏未提供时先做测试窗口验证。获得目标后，在批量开发算法前做截图与输入兼容性试验。记录“API 返回成功但画面黑/旧/缺失”等内容错误，不能只看返回码。

## 4. 技术选型核对及补充

| 项目 | 审查结果与建议 |
| --- | --- |
| .NET 10 + Avalonia 12 | 官方资料支持这一桌面组合，方向无需推翻；实际使用时锁定已验证的具体 SDK 和包版本。[Avalonia 平台要求](https://docs.avaloniaui.net/docs/supported-platforms) |
| Windows 10 22H2 | 不能只根据 FramePool 的最低版本推导整个技术栈的支持。当前 .NET 10 官方支持表未列出普通 Windows 10 22H2；将其列为项目自行验证的兼容目标，并记录实际版本/edition。兼容可运行与官方支持需区分。[.NET 10 支持平台](https://github.com/dotnet/core/blob/main/release-notes/10.0/supported-os.md) |
| OpenCvSharp | 官方当前包选择文档区分 4/5 系列，并列出 macOS ARM64 Runtime。要明确主版本、托管包和 Native 包的配套版本，不是只写库名；在 Mac 上做 Mat 创建、编解码、简单运算实验后才确认可用。[官方包选择](https://github.com/shimat/opencvsharp/blob/main/docs/docfx/articles/getting-started/package-selection.md) |
| Maa C# Binding | 原文对封装和 VC++ 依赖的方向基本正确；Binding 与 Native 版本须按兼容关系配套，不能假设版本号完全相同。[官方仓库](https://github.com/MaaXYZ/MaaFramework.Binding.CSharp) |
| 可复现构建 | `Directory.Packages.props` 只集中管理直接依赖版本；还应锁 SDK、启用 NuGet lock file 与 locked restore，并记录 Native 文件版本。CI 固定 runner 镜像大版本，记录镜像修订，而非把 `windows-latest` 当作固定环境。 |
| 发布与日志 | Native 加载实验在首次引入依赖时就做；本地日志、设置损坏恢复和退出清理从 Phase 1 开始，不等 Phase 10。正式发布再收紧依赖检查、日志保留和完整验收。 |

网页及主分支资料会变化；上述链接用于解释设计依据，实施时以最终锁定版本的 API 和真机结果为准。本次未替项目锁定依赖版本。

## 5. 推荐处理顺序

1. Phase 0–1：落实 R01–R05，交付可独立运行的窗口诊断程序。
2. Phase 2：完成 R03、R11 中的侧边栏坐标和可达性策略。
3. Phase 3：完成 R06、R09、R10 的截图契约、资源管理和诊断。
4. Phase 4：完成 R07、R08 的输入中止与清理验证。
5. Phase 6–8：实现有界实时分析与有资源上限的滚动采集/拼接。

对应可执行任务见同目录 `Phase0-1-开发清单.md`。原评审阶段将建议单独记录；后续已将这些建议合并进 V1.1，见文首归档说明。
